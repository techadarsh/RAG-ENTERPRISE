## 1. Observability Principles & Strategy

### 1.1 Three Pillars of Observability

**1. Metrics** (What is happening?):
- Numerical measurements over time
- CPU usage, memory, request rate, latency
- Aggregated data (averages, percentiles)
- Good for: Dashboards, alerts, trends

**2. Logs** (Why is it happening?):
- Discrete events with context
- Error messages, stack traces, debug info
- Searchable and filterable
- Good for: Debugging, forensics, auditing

**3. Traces** (Where is it happening?):
- Request flow across services
- Timing breakdown by component
- Parent-child relationships
- Good for: Performance optimization, bottleneck identification

### 1.2 Observability Strategy

**Instrument Everything**:
- Every API endpoint
- Every database query
- Every external service call
- Every background job

**High Cardinality Data**:
- Track user_id, conversation_id, request_id
- Enable filtering and correlation
- Support ad-hoc queries

**Continuous Improvement**:
- Add metrics when debugging
- Refine alerts based on false positives
- Update dashboards based on usage

### 3.2 Instrumenting Code

**Middleware for automatic instrumentation**:
```python
# backend/middleware.py
from fastapi import Request
import time
from .metrics import request_count, request_duration, active_requests

async def metrics_middleware(request: Request, call_next):
    # Track active requests
    active_requests.inc()
    
    # Start timer
    start_time = time.perf_counter()
    
    try:
        # Process request
        response = await call_next(request)
        
        # Record metrics
        duration = time.perf_counter() - start_time
        request_count.labels(
            method=request.method,
            endpoint=request.url.path,
            status=response.status_code
        ).inc()
        
        request_duration.labels(
            method=request.method,
            endpoint=request.url.path
        ).observe(duration)
        
        return response
    
    finally:
        active_requests.dec()
```

**Manual instrumentation**:
```python
# backend/rag_pipeline.py
from .metrics import query_duration, query_success, query_errors
import time

def query_rag(query: str, user_id: str):
    start_time = time.perf_counter()
    
    try:
        # Embed query
        embed_start = time.perf_counter()
        embedding = embed_text(query)
        query_duration.labels(stage='embedding').observe(
            time.perf_counter() - embed_start
        )
        
        # Search
        search_start = time.perf_counter()
        results = search(embedding)
        query_duration.labels(stage='search').observe(
            time.perf_counter() - search_start
        )
        
        # Generate answer
        gen_start = time.perf_counter()
        answer = generate_answer(results, query)
        query_duration.labels(stage='generation').observe(
            time.perf_counter() - gen_start
        )
        
        # Record success
        query_success.inc()
        
        # Record total duration
        query_duration.labels(stage='total').observe(
            time.perf_counter() - start_time
        )
        
        return answer
    
    except Exception as e:
        # Record error
        query_errors.labels(error_type=type(e).__name__).inc()
        raise
```

**Context manager for timing**:
```python
from contextlib import contextmanager

@contextmanager
def track_time(metric, **labels):
    """Context manager to track execution time."""
    start = time.perf_counter()
    try:
        yield
    finally:
        duration = time.perf_counter() - start
        metric.labels(**labels).observe(duration)

# Usage
with track_time(query_duration, stage='embedding'):
    embedding = embed_text(query)
```

## 5. Log Aggregation (ELK Stack)

### 5.1 Structured Logging

**Configure Python logging**:
```python
# backend/logging_config.py
import logging
import json
from datetime import datetime

class JSONFormatter(logging.Formatter):
    """Format logs as JSON for Elasticsearch."""
    
    def format(self, record):
        log_data = {
            'timestamp': datetime.utcnow().isoformat(),
            'level': record.levelname,
            'logger': record.name,
            'message': record.getMessage(),
            'module': record.module,
            'function': record.funcName,
            'line': record.lineno,
        }
        
        # Add exception info if present
        if record.exc_info:
            log_data['exception'] = self.formatException(record.exc_info)
        
        # Add extra fields
        if hasattr(record, 'user_id'):
            log_data['user_id'] = record.user_id
        if hasattr(record, 'request_id'):
            log_data['request_id'] = record.request_id
        if hasattr(record, 'duration_ms'):
            log_data['duration_ms'] = record.duration_ms
        
        return json.dumps(log_data)

# Configure logger
def setup_logging():
    logger = logging.getLogger()
    logger.setLevel(logging.INFO)
    
    handler = logging.StreamHandler()
    handler.setFormatter(JSONFormatter())
    logger.addHandler(handler)
    
    return logger

logger = setup_logging()
```

**Usage**:
```python
# backend/rag_pipeline.py
import logging

logger = logging.getLogger(__name__)

def query_rag(query: str, user_id: str, request_id: str):
    logger.info(
        "Processing query",
        extra={
            'user_id': user_id,
            'request_id': request_id,
            'query_length': len(query)
        }
    )
    
    try:
        result = process_query(query)
        
        logger.info(
            "Query completed successfully",
            extra={
                'user_id': user_id,
                'request_id': request_id,
                'duration_ms': result['processing_time_ms']
            }
        )
        
        return result
    
    except Exception as e:
        logger.error(
            "Query failed",
            extra={
                'user_id': user_id,
                'request_id': request_id,
                'error_type': type(e).__name__
            },
            exc_info=True
        )
        raise
```

```python
    # Configure Jaeger exporter
    jaeger_exporter = JaegerExporter(
        agent_host_name="jaeger",
        agent_port=6831,
    )
    
    # Add span processor
    provider.add_span_processor(
        BatchSpanProcessor(jaeger_exporter)
    )
    
    # Instrument FastAPI
    FastAPIInstrumentor.instrument_app(app)
    
    return trace.get_tracer(__name__)

# Usage in main.py
tracer = setup_tracing(app)
```

```python
# backend/rag_pipeline.py
from opentelemetry import trace

tracer = trace.get_tracer(__name__)

def query_rag(query: str, user_id: str):
    with tracer.start_as_current_span("query_rag") as span:
        # Add attributes
        span.set_attribute("user_id", user_id)
        span.set_attribute("query_length", len(query))
        
        # Embed query

            embed_span.set_attribute("embedding_dim", len(embedding))

            results = search(embedding)
            search_span.set_attribute("results_count", len(results))
            search_span.set_attribute("top_score", results[0]['score'])
        
        # Generate answer
        with tracer.start_as_current_span("generate") as gen_span:
            answer = generate_answer(results, query)
            gen_span.set_attribute("answer_length", len(answer))
        
        return answer
```

## 8. Health Checks & Uptime Monitoring

### 8.1 Health Check Endpoint

**Comprehensive health check**:
```python
# backend/main.py
from fastapi import FastAPI, status
from typing import Dict

@app.get("/health", status_code=status.HTTP_200_OK)
async def health_check() -> Dict:
    """
    Comprehensive health check endpoint.
    Returns 200 if all components healthy, 503 otherwise.
    """
    health_status = {
        "status": "healthy",
        "version": "1.0.0",
        "timestamp": datetime.utcnow().isoformat(),
        "components": {}
    }
    
    # Check Milvus
    try:
        milvus_client.health_check()
        health_status["components"]["milvus"] = "healthy"
    except Exception as e:
        health_status["components"]["milvus"] = f"unhealthy: {str(e)}"
        health_status["status"] = "degraded"
    
    # Check Ollama
    try:
        response = requests.get("http://ollama:11434/api/tags", timeout=2)
        if response.status_code == 200:
            health_status["components"]["ollama"] = "healthy"
        else:
            health_status["components"]["ollama"] = "unhealthy"
            health_status["status"] = "degraded"
    except Exception as e:
        health_status["components"]["ollama"] = f"unhealthy: {str(e)}"
        health_status["status"] = "degraded"
    
    # Check Redis cache
    try:
        redis_client.ping()
        health_status["components"]["redis"] = "healthy"
    except Exception as e:
        health_status["components"]["redis"] = f"unhealthy: {str(e)}"
        health_status["status"] = "degraded"
    
    # Set status code based on health
    if health_status["status"] == "healthy":
        return health_status
    else:
        return JSONResponse(
            status_code=status.HTTP_503_SERVICE_UNAVAILABLE,
            content=health_status
        )

# Liveness probe (is service running?)
@app.get("/healthz")
async def liveness():
    return {"status": "alive"}

# Readiness probe (is service ready to serve traffic?)
@app.get("/ready")
async def readiness():
    # Check if service is ready
    try:
        # Verify critical components
        milvus_client.health_check()
        return {"status": "ready"}
    except:
        return JSONResponse(
            status_code=status.HTTP_503_SERVICE_UNAVAILABLE,
            content={"status": "not ready"}
        )
```

## 11. On-Call Runbooks

### 11.1 High Error Rate Runbook

**Alert**: HighErrorRate
**Severity**: Critical
**Threshold**: Error rate >1% for 2 minutes

**Investigation Steps**:

1. **Check Grafana dashboard**: http://grafana:3000/d/rag-system
   - Verify error rate spike
   - Identify affected endpoints

2. **Check recent logs** in Kibana:
   ```
   level: "ERROR" AND @timestamp >= now-15m | sort @timestamp desc
   ```
   - Look for common error patterns
   - Identify error types

3. **Check traces** in Jaeger:
   - Find failing traces
   - Identify which span is failing

4. **Common causes**:
   - Milvus connection issue → Check Milvus health
   - Ollama timeout → Check Ollama status and load
   - Database connection pool exhausted → Check active connections
   - Invalid input → Check input validation

**Resolution**:
- If Milvus down: Restart Milvus container
- If Ollama overloaded: Scale horizontally or add GPU
- If connection pool exhausted: Increase pool size
- If input validation issue: Deploy fix

**Verification**:
- Error rate returns to <0.5%
- User queries succeed
- No new alerts triggered

---

### 11.2 High Latency Runbook

**Alert**: HighLatency
**Severity**: Warning
**Threshold**: P95 latency >5s for 5 minutes

**Investigation Steps**:

1. **Check latency breakdown** in Grafana:
   ```promql
   histogram_quantile(0.95, 
     rate(rag_query_duration_seconds_bucket{stage=~"embedding|search|generation"}[5m])
   )
   ```
   - Identify slowest stage

2. **If embedding slow**:
   - Check CPU/GPU utilization
   - Check for batch processing issues
   - Verify embedding cache working

3. **If search slow**:
   - Check Milvus metrics
   - Verify index parameters
   - Check for data growth (re-index needed?)

4. **If generation slow**:
   - Check Ollama metrics
   - Verify no model loading delays
   - Check for context size issues

**Resolution**:
- Scale resources (CPU/GPU)
- Enable/optimize caching
- Tune parameters (batch size, index settings)
- Optimize prompts (reduce context size)

---

### 11.3 Service Down Runbook

**Alert**: ServiceDown
**Severity**: Critical
**Threshold**: Service down for 1 minute

**Investigation Steps**:

1. **Check service status**:
   ```bash
   docker ps | grep backend
   ```

2. **Check logs**:
   ```bash
   docker logs backend --tail 100
   ```

3. **Common causes**:
   - Container crashed → Check OOM, exceptions
   - Port conflict → Check port bindings
   - Dependency unavailable → Check Milvus, Ollama, Redis

**Resolution**:

1. **Restart service**:

2. **If doesn't help, check dependencies**:

3. **Restart full stack if needed**:
   ```bash
   docker-compose down
   docker-compose up -d
   ```

**Verification**:
- Service returns 200 on /health
- Queries succeed
- Metrics resuming

## 12. Incident Response Procedures

### 12.1 Incident Severity Levels

```
SEV 1 (Critical):
- System completely down
- Data loss or corruption
- Security breach
- Response: Immediate, page on-call

SEV 2 (High):
- Major feature broken
- High error rate (>5%)
- Severe performance degradation
- Response: Within 30 minutes

SEV 3 (Medium):
- Minor feature broken
- Moderate performance issues
- Response: Within 4 hours

SEV 4 (Low):
- Cosmetic issues
- Non-critical bugs
- Response: Best effort
```

### 12.2 Incident Response Process

**1. Detection** (0-5 minutes):
- Alert triggers
- On-call engineer acknowledges

**2. Triage** (5-15 minutes):
- Assess severity
- Determine impact
- Identify affected users/systems

**3. Mitigation** (15-60 minutes):
- Stop bleeding (rollback, scale, disable)
- Communicate status
- Implement temporary fix

**4. Resolution** (1-4 hours):
- Root cause analysis
- Permanent fix
- Deploy fix
- Verify resolution

**5. Post-Mortem** (within 1 week):
- Document incident
- Identify preventions
- Create action items
- Update runbooks

## 13. Monitoring Best Practices

### 13.1 Dos and Don'ts

**DO**:
- ✅ Monitor what matters (user-facing metrics)
- ✅ Set meaningful alert thresholds
- ✅ Use SLIs (Service Level Indicators)
- ✅ Implement error budgets
- ✅ Review and adjust alerts regularly
- ✅ Document runbooks
- ✅ Practice incident response

**DON'T**:
- ❌ Alert on everything (alert fatigue)
- ❌ Use default thresholds blindly
- ❌ Monitor vanity metrics only
- ❌ Ignore false positives
- ❌ Let dashboards go stale
- ❌ Skip post-mortems

### 13.2 Golden Signals

**Four Golden Signals** (SRE):
1. **Latency**: How long requests take
2. **Traffic**: How many requests
3. **Errors**: How many requests fail
4. **Saturation**: How full your service is

**Monitor all four** for complete visibility

### 13.3 SLIs and SLOs

**Service Level Indicators (SLIs)**:
- Request success rate
- P95 latency
- Uptime

**Service Level Objectives (SLOs)**:
```
SLI                  | SLO Target | Error Budget (30 days)
---------------------|------------|------------------------
Success Rate         | 99.9%      | 0.1% (43 minutes)
P95 Latency          | <2.5s      | 5% requests >2.5s
Uptime               | 99.9%      | 43 minutes downtime
```

**Error Budget** = (1 - SLO) × time period
- If error budget spent: Focus on reliability
- If error budget remains: Ship new features
