## 1. System Overview

### Purpose & Vision

The RAG Enterprise Chatbot serves as an intelligent knowledge retrieval system that enables employees to:
- Query company documentation using natural language
- Get instant answers backed by source citations
- Access policy information without manual document searching
- Learn about technical implementations and best practices
- Understand system architecture and design decisions

### Key Capabilities

**Natural Language Understanding**
- Accepts queries in conversational English
- Handles multi-turn conversations with context retention
- Supports follow-up questions and clarifications
- Understands synonyms and related terminology

**Semantic Search**
- Vector-based similarity matching using dense embeddings
- Retrieves top-K most relevant document chunks
- Considers semantic meaning, not just keyword matching
- Returns relevance scores for transparency

**Context-Aware Generation**
- Generates answers based on retrieved documentation
- Includes source attribution for verification
- Maintains conversation history (5 previous turns)
- Provides concise, accurate responses

### Business Value

1. **Reduced Search Time**: 80% faster than manual document search
2. **Improved Accuracy**: Answers backed by actual documentation
3. **Onboarding Efficiency**: New employees get instant policy answers
4. **Knowledge Democratization**: Everyone has access to enterprise knowledge
5. **Audit Trail**: All queries and responses logged for compliance

## 3. Technology Stack Decisions

### Backend: FastAPI (Python 3.10+)

**Why FastAPI?**
- **Async Support**: Native async/await for concurrent request handling
- **Automatic Documentation**: OpenAPI (Swagger) docs generated automatically
- **Type Safety**: Pydantic models ensure request/response validation
- **Performance**: One of the fastest Python frameworks (comparable to Node.js)
- **ML Integration**: Seamless integration with Python ML ecosystem

**Alternatives Considered**:
- Flask: Lacks async support, requires more boilerplate
- Django: Too heavyweight for this use case
- Node.js: Would require separate Python service for ML models

### Vector Database: Milvus

**Why Milvus?**
- **Purpose-Built**: Designed specifically for vector similarity search
- **Performance**: Optimized ANN (Approximate Nearest Neighbor) algorithms
- **Scalability**: Handles billion-scale vector collections
- **HNSW Index**: Hierarchical Navigable Small World graphs for fast retrieval
- **Open Source**: No vendor lock-in, active community

**Key Specifications**:
- Collection: `enterprise_docs`
- Index Type: HNSW (Hierarchical Navigable Small World)
- Metric: Cosine similarity (IP - Inner Product)
- Vector Dimension: 1024 (BGE-Large-En)
- Top-K Retrieval: 3 documents per query

**Alternatives Considered**:
- Pinecone: Cloud-only, paid service, vendor lock-in
- Weaviate: Less mature, smaller community
- Chroma: Simpler but less performant at scale
- FAISS: Library not database, lacks query filtering

### Embedding Model: BGE-Large-En-v1.5

**Why BGE-Large-En?**
- **SOTA Performance**: Top rankings on MTEB leaderboard
- **Dense Retrieval**: Excels at semantic similarity tasks
- **1024 Dimensions**: Rich semantic representation
- **Zero-Shot**: Works without fine-tuning on enterprise docs
- **HuggingFace**: Easy to load and use

**Model Characteristics**:
- Architecture: BERT-based encoder
- Parameters: 335M
- Max Sequence Length: 512 tokens
- Output: 1024-dimensional dense vector
- Normalization: L2-normalized embeddings

**Alternatives Considered**:
- all-MiniLM-L6-v2: Smaller (384 dim) but lower quality
- OpenAI text-embedding-ada-002: Expensive, requires API calls
- Instructor embeddings: Requires task instructions

### LLM: Mistral 7B (Ollama)

**Why Mistral 7B?**
- **Quality**: Outperforms Llama-2 13B on most benchmarks
- **Efficiency**: Only 7B parameters, runs on consumer hardware
- **Context Window**: 8K tokens (enough for RAG context)
- **Licensing**: Apache 2.0 (permissive for commercial use)
- **Local Inference**: Via Ollama, no API costs

**Inference Configuration**:
- Temperature: 0.3 (balanced creativity/consistency)
- Top-P: 0.9 (nucleus sampling)
- Max Tokens: 500 (concise answers)
- Stream: True (real-time response streaming)

**Alternatives Considered**:
- GPT-3.5/4: Expensive API calls, data privacy concerns
- Llama-2: Slightly lower quality than Mistral
- Falcon: Less optimized for instruction following

### Frontend: React 18

**Why React?**
- **Component Model**: Reusable UI components
- **Virtual DOM**: Efficient updates for chat interface
- **Ecosystem**: Rich library ecosystem for UI components
- **Hooks**: Simple state management for chat history
- **Developer Experience**: Hot reloading, great tooling

**Key Libraries Used**:
- react-markdown: Render formatted responses
- CSS3 animations: Typing indicators, smooth transitions

### Containerization: Docker & Docker Compose

**Why Docker?**
- **Consistency**: Same environment dev to prod
- **Isolation**: Each service in its own container
- **Portability**: Run anywhere Docker runs
- **Multi-Service**: Docker Compose orchestrates 6 services
- **Resource Control**: Memory/CPU limits per container

**Container Architecture**:
```
docker-compose.yml
├── frontend (React + Nginx)
├── backend (FastAPI + Python)
├── milvus-standalone (Vector DB)
├── etcd (Milvus metadata)
├── minio (Milvus object storage)
└── ollama (LLM inference)
```

## 4. Component Deep Dive

### 4.1 Embedding Service (`embeddings.py`)

**Responsibilities**:
- Load embedding model from HuggingFace
- Generate dense vectors for text input
- Normalize embeddings (L2 norm)
- Handle batching for efficiency

**Implementation Details**:

```python
class EmbeddingModel:
    def __init__(self):
        # Load BGE-Large-En model
        self.model = SentenceTransformer('BAAI/bge-large-en-v1.5')
        self.dimension = 1024
    
    def encode(self, texts: List[str]) -> np.ndarray:
        # Generate embeddings
        embeddings = self.model.encode(
            texts,
            normalize_embeddings=True,  # L2 normalization
            show_progress_bar=False
        )
        return embeddings
```

**Performance**:
- Single text encoding: ~50-100ms
- Batch encoding (10 docs): ~300-500ms
- GPU acceleration: Not required (CPU sufficient)

**Memory Usage**:
- Model size: ~1.2GB
- Runtime memory: ~2GB

### 4.3 RAG Pipeline (`rag_pipeline.py`)

**Responsibilities**:
- Orchestrate the entire RAG workflow
- Manage conversation context
- Coordinate embedding, retrieval, and generation
- Track performance metrics

**Workflow**:

```python
class RAGPipeline:
    def process_query(self, query: str, conversation_history: List[Dict]):
        # 1. Embed the query
        start_embed = time.time()
        query_embedding = self.embedder.encode([query])[0]
        embed_time = (time.time() - start_embed) * 1000
        
        # 2. Retrieve relevant documents
        start_retrieve = time.time()
        results = self.milvus.search(query_embedding, top_k=3)
        retrieve_time = (time.time() - start_retrieve) * 1000
        
        # 3. Build context from retrieved docs
        context = self._build_context(results)
        
        # 4. Generate answer with LLM
        start_generate = time.time()
        answer = self.llm.generate(query, context, conversation_history)
        generate_time = (time.time() - start_generate) * 1000
        
        # 5. Return response with metadata
        return {
            "answer": answer,
            "sources": results,
            "metrics": {
                "embedding_ms": embed_time,
                "retrieval_ms": retrieve_time,
                "generation_ms": generate_time,
                "total_ms": embed_time + retrieve_time + generate_time
            }
        }
```

**Context Building**:

```python
def _build_context(self, results: List[Dict]) -> str:
    context_parts = []
    for i, result in enumerate(results, 1):
        context_parts.append(f"""
        Document {i}: {result['title']}
        Content: {result['content']}
        Relevance Score: {result['score']:.2%}
        """)
    return "\n\n".join(context_parts)
```

### 4.4 LLM Client (`llm_client.py`)

**Responsibilities**:
- Interface with Ollama API
- Format prompts with system instructions
- Stream responses in real-time
- Handle conversation context

**Prompt Template**:

```python
SYSTEM_PROMPT = """You are an enterprise AI assistant with access to company documentation.

Your responsibilities:
1. Answer questions using ONLY the provided context documents
2. Cite sources by referencing document titles
3. Admit when you don't have enough information
4. Be concise but comprehensive
5. Maintain professional tone

Guidelines:
- If the context doesn't contain the answer, say "I don't have information about that in the available documents."
- Always mention which document(s) you're referencing
- For policy questions, quote exact text when relevant
- For technical questions, provide step-by-step guidance
"""

def format_prompt(query: str, context: str, history: List[Dict]) -> str:
    # Include conversation history
    history_text = ""
    for turn in history[-5:]:  # Last 5 turns
        history_text += f"User: {turn['query']}\nAssistant: {turn['response']}\n\n"
    
    prompt = f"""
    {SYSTEM_PROMPT}
    
    Previous Conversation:
    {history_text}
    
    Context Documents:
    {context}
    
    Current Question: {query}
    
    Answer:
    """
    return prompt
```

**Streaming Implementation**:

```python
def generate_stream(self, prompt: str):
    response = requests.post(
        f"{self.api_url}/api/generate",
        json={
            "model": "mistral",
            "prompt": prompt,
            "stream": True,
            "options": {
                "temperature": 0.3,
                "top_p": 0.9,
                "max_tokens": 500
            }
        },
        stream=True
    )
    
    for line in response.iter_lines():
        if line:
            chunk = json.loads(line)
            yield chunk["response"]
```

### 4.5 Document Ingestion (`confluence_ingest.py`)

**Responsibilities**:
- Load documents from filesystem
- Chunk large documents intelligently
- Generate embeddings for chunks
- Insert into Milvus with metadata

**Chunking Strategy**:

```python
def chunk_document(content: str, chunk_size: int = 1000, overlap: int = 200):
    """
    Split document into overlapping chunks.
    
    Strategy:
    - Respect sentence boundaries (don't split mid-sentence)
    - 1000 char chunks (fits in model context)
    - 200 char overlap (maintains continuity)
    """
    sentences = content.split('. ')
    chunks = []
    current_chunk = ""
    
    for sentence in sentences:
        if len(current_chunk) + len(sentence) < chunk_size:
            current_chunk += sentence + ". "
        else:
            if current_chunk:
                chunks.append(current_chunk.strip())
            # Start new chunk with overlap
            current_chunk = current_chunk[-overlap:] + sentence + ". "
    
    if current_chunk:
        chunks.append(current_chunk.strip())
    
    return chunks
```

**Why This Chunking?**
- 1000 chars ≈ 200-250 tokens (fits model context)
- Overlap ensures context continuity across chunks
- Sentence-aware splitting preserves meaning
- Smaller chunks = better retrieval precision

**Ingestion Pipeline**:

```python
def ingest_documents(document_dir: str):
    for file in os.listdir(document_dir):
        # 1. Read document
        content = read_file(file)
        
        # 2. Chunk document
        chunks = chunk_document(content)
        
        # 3. Generate embeddings
        embeddings = embedder.encode(chunks)
        
        # 4. Insert to Milvus
        for chunk, embedding in zip(chunks, embeddings):
            milvus.insert({
                "title": f"{file} (Part {i}/{len(chunks)})",
                "content": chunk,
                "embedding": embedding,
                "metadata": {
                    "source_file": file,
                    "chunk_index": i,
                    "total_chunks": len(chunks)
                }
            })
```

## 6. Security & Privacy Architecture

### Privacy Guarantees

**1. 100% On-Premise Deployment**
- All services run in local Docker containers
- No external API calls (except optional OpenAI mode)
- Data never leaves your infrastructure

**2. Data Sovereignty**
- Vector embeddings stored in local Milvus
- Conversation history stored in-memory (optional Redis)
- No cloud storage dependencies

**3. Network Isolation**
- Backend accessible only from frontend
- Milvus not exposed to external network
- Container-to-container communication via Docker network

### Security Considerations

**Authentication & Authorization** (Future Enhancement)
- Currently: No authentication (POC only)
- Planned: JWT-based authentication
- Role-based access control (RBAC) for different document sets

**Input Validation**
- Query length limits (max 2000 chars)
- Pydantic models validate request structure
- SQL injection protection (Milvus uses parameterized queries)

**Rate Limiting** (Future Enhancement)
- Per-user query limits
- Prevent abuse and ensure fair usage

**Audit Logging**
- All queries logged with timestamps
- Source documents tracked
- User IDs recorded (when auth implemented)

## 9. Scalability Considerations

### Horizontal Scaling

**Backend Scaling**:
```bash
docker compose up --scale backend=3
```
- Add load balancer (Nginx/Traefik)
- Stateless design enables easy scaling
- Share Milvus and Ollama instances

**Milvus Scaling**:
- Move to Milvus cluster mode
- Separate query and data nodes
- Distribute index across nodes

### Vertical Scaling

**GPU Acceleration**:
- Add NVIDIA GPU for LLM inference
- 2-4x faster generation (500ms vs 1200ms)
- Requires CUDA-enabled Ollama

**Memory Optimization**:
- Use quantized models (Q4, Q5)
- Smaller memory footprint (4GB vs 8GB)
- Slight quality degradation

### Caching Strategy

**Query Caching** (Future):
```python
# Redis cache for frequent queries
@cache(ttl=3600)  # 1 hour cache
def process_query(query: str):
    # Expensive RAG pipeline
    pass
```

**Embedding Caching**:
- Cache query embeddings
- Avoid re-encoding identical queries
- 50ms saved per cached query

### Database Optimization

**Milvus Tuning**:
- Increase `ef` for better accuracy (slower)
- Decrease `ef` for faster search (less accurate)
- Partition collection by document type
- Use GPU-enabled index (IVF_FLAT_GPU)
