## 1. Information Security Framework

### 1.1 Security Objectives

**CIA Triad**:

**Confidentiality**:
- Only authorized individuals can access sensitive information
- Data protected from unauthorized disclosure
- Encryption used for data at rest and in transit

**Integrity**:
- Data accurate and unaltered
- Changes logged and traceable
- Protection against unauthorized modification

**Availability**:
- Systems and data accessible when needed
- Target uptime: 99.9% (8.76 hours downtime/year)
- Backup and recovery procedures in place

### 1.2 Security Principles

**Defense in Depth**:
- Multiple layers of security controls
- If one layer fails, others still protect
- Examples: Firewall + WAF + Application security + Encryption

**Least Privilege**:
- Users get minimum access needed for their role
- No default admin access
- Regular access reviews (quarterly)

**Zero Trust**:
- Never trust, always verify
- Authenticate and authorize every request
- Network location doesn't imply trust

**Privacy by Design**:
- Privacy built into systems from start (not added later)
- Data minimization (collect only what's needed)
- Purpose limitation (use data only for stated purpose)

### 1.3 Security Governance

**Security Team**:
- **Chief Information Security Officer (CISO)**: Overall security strategy
- **Security Engineer**: Implement security controls, monitor threats
- **Security Analyst**: Monitor security events, investigate incidents
- **Compliance Manager**: Ensure regulatory compliance

**Security Committee**:
- Meets quarterly
- Members: CISO, VP Engineering, VP Legal, CTO
- Reviews: Security posture, incidents, compliance status, budget

**Security Budget**: 5% of IT budget allocated to security

## 2. Access Control & Authentication

### 2.1 Identity Management

**User Account Lifecycle**:

**Provisioning** (Day 1):
- IT creates accounts after HR onboarding
- Access based on role (RBAC - Role-Based Access Control)
- Default permissions: Email, Slack, VPN, minimal access
- Manager requests additional access (via Jira ticket)

**Changes** (During Employment):
- Role change: Access adjusted within 24 hours
- New system access: Manager approval required
- Temporary elevated access: Approved for specific duration

**De-provisioning** (Last Day):
- Immediate: Revoke VPN, email, Slack, SSH keys
- Within 24 hours: Revoke all system access
- Checklist: 30+ systems reviewed
- Accounts disabled (not deleted) for audit trail

**Account Review** (Quarterly):
- Managers review team access
- Remove unused accounts
- Downgrade over-privileged accounts
- Report sent to security team

### 2.2 Authentication Standards

**Password Requirements**:
- **Minimum Length**: 12 characters
- **Complexity**: Must include:
  - Uppercase letter
  - Lowercase letter
  - Number
  - Special character (!@#$%^&*)
- **Expiration**: 90 days (prompted to change)
- **History**: Cannot reuse last 5 passwords
- **Lockout**: 5 failed attempts → 30-minute lockout

**Password Examples**:
-  Weak: `password123`, `Company2025`, `Welcome1!`
-  Strong: `Tr0ub4dor&3$Ketch`, `correct-horse-battery-staple-2025!`

**Password Storage**:
- Never store plaintext passwords
- Use bcrypt or Argon2 (industry-standard hashing)
- Salt every password (unique salt per password)

**Password Manager**:
- Company provides: 1Password or LastPass (choose one)
- Use for all work passwords
- Generate random passwords (16+ characters)
- Shared vaults for team credentials (encrypted)

### 2.3 Multi-Factor Authentication (MFA)

**MFA Required For**:
-  VPN access (all users)
-  Email (all users)
-  AWS Console (all users)
-  GitHub (all users)
-  Admin accounts (databases, servers)
-  Financial systems (payroll, expenses)
-  Customer data access

**MFA Methods** (in order of preference):
1. **Authenticator App** (preferred): Google Authenticator, Microsoft Authenticator, Authy
2. **Hardware Token**: YubiKey (provided for admins)
3. **SMS** (least secure, only if others unavailable)

**MFA Setup**:
```
1. Install authenticator app (phone or desktop)
2. Log into service → Security Settings → Enable 2FA
3. Scan QR code with authenticator app
4. Save backup codes (in password manager)
5. Test: Log out and log back in (should prompt for MFA)
```

**Backup Codes**:
- Save 10 backup codes (one-time use)
- Store in password manager
- Use if phone lost or authenticator app unavailable

### 2.4 Privileged Access Management

**Privileged Accounts**:
- Admin accounts (root, Administrator)
- Database admin accounts
- AWS admin access
- Production server SSH access

**Privileged Access Rules**:
-  No shared accounts (each person has own admin account)
-  No default admin access (request when needed)
-  Just-in-time access (temporary elevated access)
-  Session recording (all admin sessions logged)
-  MFA required (hardware token preferred)

**Just-in-Time Access**:
```
1. Engineer needs admin access for specific task
2. Submit request via security portal: "Need database admin for schema migration"
3. Manager approves (or auto-approved for routine tasks)
4. Access granted for 4 hours (or task duration)
5. Access automatically revoked after expiration
6. All actions logged and audited
```

**Privileged Session Recording**:
- All admin sessions recorded (video + commands)
- Stored for 1 year
- Reviewed if incident occurs
- Alerts on suspicious commands (rm -rf, DROP TABLE, etc.)

### 2.5 SSH Key Management

**SSH Keys**:
- Required for server access (no password login)
- Key length: Minimum 2048-bit RSA or 256-bit Ed25519
- Passphrase required (protect private key)

**SSH Key Lifecycle**:
```bash
# 1. Generate key pair
ssh-keygen -t ed25519 -C "your.email@company.com"
# Enter passphrase when prompted

# 2. Add public key to server (IT manages)
cat ~/.ssh/id_ed25519.pub
# Send public key to IT (never send private key!)

# 3. Test connection
ssh user@server.company.com

# 4. Key rotation (annually)
# Generate new key pair, replace old public key on servers
```

**SSH Key Revocation**:
- Employee leaves: Remove public key from all servers immediately
- Key compromised: Revoke immediately, investigate access logs

## 3. Data Classification & Handling

### 3.1 Data Classification Levels

**PUBLIC**:
- **Definition**: Information intended for public consumption
- **Examples**: Marketing materials, press releases, public website content, open-source code
- **Handling**: Can be shared freely, no encryption required
- **Storage**: Anywhere (public GitHub, public website)
- **Label**: Not required

**INTERNAL**:
- **Definition**: Information for internal use only
- **Examples**: Internal memos, project docs, source code (proprietary), internal Slack messages
- **Handling**: Share only with employees, basic access controls
- **Storage**: Company systems only (Google Drive, Confluence, GitHub private repos)
- **Label**: Mark as "Internal" in header/footer

**CONFIDENTIAL**:
- **Definition**: Sensitive business information, limited distribution
- **Examples**: Financial data, customer lists, contracts, employee data (salaries, reviews), product roadmaps, business strategies
- **Handling**: Share only on need-to-know basis, encryption recommended
- **Storage**: Encrypted storage (Google Drive with encryption, encrypted databases)
- **Label**: Mark as "Confidential" in header/footer, watermark PDFs

**RESTRICTED**:
- **Definition**: Highly sensitive data, legal/regulatory protections
- **Examples**: Social Security Numbers, payment card data (PCI), health information (HIPAA), trade secrets, passwords, encryption keys
- **Handling**: Strict access controls, encryption required at rest and in transit
- **Storage**: Encrypted databases, access logging enabled
- **Label**: Mark as "Restricted" in header/footer, DLP (Data Loss Prevention) monitoring

### 3.2 Data Handling Requirements

**Summary Table**:

```
CLASSIFICATION | ENCRYPTION | ACCESS      | SHARING            | DISPOSAL
---------------|------------|-------------|--------------------|------------------
PUBLIC         | Optional   | Anyone      | Freely             | Delete (no special handling)
INTERNAL       | Optional   | Employees   | Internal only      | Delete securely
CONFIDENTIAL   | Recommended| Need-to-know| Approved only      | Secure delete (7x overwrite)
RESTRICTED     | Required   | Authorized  | Explicit approval  | Certified destruction
```

### 3.3 Data Handling Procedures

**Encryption Requirements**:

**At Rest**:
- Confidential: AES-256 encryption
- Restricted: AES-256 + hardware encryption (HSM)
- Databases: Transparent Data Encryption (TDE)
- Files: Encrypt folders/files containing sensitive data

**In Transit**:
- All network traffic: TLS 1.3 (minimum TLS 1.2)
- APIs: HTTPS only (no HTTP)
- Emails with attachments: Encrypt attachments (password-protected ZIP or encrypted PDF)
- File transfers: SFTP or encrypted cloud storage links

**Email Handling**:
- **Public/Internal**: Regular email
- **Confidential**: Encrypted email or encrypted attachment
- **Restricted**: Encrypted email + password-protected attachment, password shared via separate channel (phone, SMS)

**Example Encryption**:
```bash
# Encrypt file with GPG
gpg --symmetric --cipher-algo AES256 confidential_document.pdf
# Creates: confidential_document.pdf.gpg

# Decrypt
gpg confidential_document.pdf.gpg
```

**Printing**:
- Confidential/Restricted: Print only when necessary
- Use secure print (requires badge/PIN at printer)
- Collect printouts immediately
- Shred when no longer needed

**Data Disposal**:

**Digital Data**:
- **Internal**: Regular deletion (Trash → Empty Trash)
- **Confidential**: Secure deletion (7x overwrite with `shred` or `srm`)
- **Restricted**: Certified destruction (use certified data destruction service)

```bash
# Secure delete file (7x overwrite)
shred -vfz -n 7 sensitive_file.txt

# Secure delete disk (before disposing hardware)
dd if=/dev/zero of=/dev/sdX bs=1M
# OR use DBAN (Darik's Boot and Nuke)
```

**Physical Media**:
- Paper: Shred (cross-cut shredder, particles <4mm)
- Hard drives: Physical destruction (drill holes) or degaussing + shredding
- USB drives: Physical destruction (hammer, drill)
- Use certified destruction vendor (certificate of destruction provided)

## 4. Network Security

### 4.1 Network Architecture

**Network Segmentation**:

```
Internet
   |
[Firewall/WAF]
   |
   ├─ DMZ (Public-facing)
   │    ├─ Frontend servers
   │    └─ API Gateway
   |
   ├─ Application Tier
   │    ├─ Backend servers
   │    └─ Application servers
   |
   └─ Data Tier (Most Restricted)
        ├─ Databases (Milvus, PostgreSQL)
        └─ Internal services
```

**Firewall Rules**:
- Default deny all traffic
- Whitelist specific ports and sources
- Regular firewall rule review (quarterly)

**Example Rules**:
```
# Allow HTTPS from anywhere to frontend
ALLOW TCP 443 FROM 0.0.0.0/0 TO frontend

# Allow backend to talk to database
ALLOW TCP 19530 FROM backend TO milvus

# Deny everything else
DENY ALL
```

### 4.2 VPN Access

**VPN Required For**:
- Accessing company network remotely
- Accessing internal tools (Jira, Confluence, databases)
- Working from public Wi-Fi

**VPN Configuration**:
- **Protocol**: OpenVPN or WireGuard
- **Encryption**: AES-256
- **Authentication**: Username + Password + MFA
- **Split Tunneling**: Work traffic via VPN, personal traffic direct

**VPN Setup**:
```
1. Install VPN client (Cisco AnyConnect or OpenVPN)
2. Import VPN profile (provided by IT)
3. Connect: Enter username, password, MFA code
4. Verify connection: Check IP address (should be company IP)
```

**VPN Monitoring**:
- All VPN connections logged
- Alerts on unusual patterns (login from multiple countries, excessive data transfer)

### 4.3 Wi-Fi Security

**Office Wi-Fi**:
- **Corporate Network**: WPA3 encryption, 802.1X authentication (username/password)
- **Guest Network**: Separate network, no access to internal resources, bandwidth limited

**Home Wi-Fi** (for remote workers):
- Change default router password
- Use WPA3 (or WPA2 if router older)
- Disable WPS (security vulnerability)
- Update router firmware regularly
- Use guest network for IoT devices (separate from work devices)

### 4.4 Network Monitoring

**Intrusion Detection System (IDS)**:
- Monitors network traffic for suspicious patterns
- Alerts on: Port scans, brute force attempts, malware traffic, data exfiltration

**Network Flow Analysis**:
- Log all network connections (source, destination, port, bytes)
- Detect anomalies (unusual traffic patterns, large data transfers)
- Retention: 90 days

**DDoS Protection**:
- Use CloudFlare or AWS Shield
- Rate limiting (max requests per IP)
- Automatic blocking of malicious IPs

## 5. Application Security

### 5.1 Secure Development Lifecycle (SDLC)

**Security Gates**:

**Phase 1: Design**:
- Threat modeling (identify potential threats)
- Security requirements defined
- Privacy impact assessment (for user data)

**Phase 2: Development**:
- Secure coding guidelines followed
- Code reviews (security focus)
- Static code analysis (SonarQube, Bandit)

**Phase 3: Testing**:
- Security testing (OWASP Top 10 vulnerabilities)
- Penetration testing (for major releases)
- Dependency scanning (vulnerable libraries)

**Phase 4: Deployment**:
- Security approval required
- Environment hardening (disable unnecessary services)
- Secret management (no hardcoded passwords)

**Phase 5: Operations**:
- Security monitoring (logs, alerts)
- Incident response plan
- Regular security patches

### 5.2 Secure Coding Practices

**Input Validation**:
```python
#  Bad: No validation (SQL injection risk)
query = f"SELECT * FROM users WHERE username = '{username}'"

#  Good: Parameterized query
query = "SELECT * FROM users WHERE username = ?"
cursor.execute(query, (username,))
```

**Authentication & Authorization**:
```python
#  Check authentication
@require_authentication
def protected_endpoint():
    # ...

#  Check authorization
@require_role("admin")
def admin_endpoint():
    # ...
```

**Output Encoding** (prevent XSS):
```python
#  Bad: Direct HTML output (XSS risk)
return f"<div>Welcome {username}</div>"

#  Good: Escaped output
from html import escape
return f"<div>Welcome {escape(username)}</div>"
```

**Error Handling**:
```python
#  Bad: Exposes sensitive info
except Exception as e:
    return f"Error: {str(e)}"  # Might expose stack trace, database info

#  Good: Generic error message
except Exception as e:
    logger.error(f"Error processing request: {e}")
    return "An error occurred. Please contact support."
```

**Secret Management**:
```python
#  Bad: Hardcoded secret
API_KEY = "sk-1234567890abcdef"

#  Good: Environment variable
import os
API_KEY = os.getenv("API_KEY")

#  Better: Secret management service
from aws_secretsmanager import get_secret
API_KEY = get_secret("api-key")
```

### 5.3 Dependency Management

**Vulnerability Scanning**:
- Scan dependencies weekly (automated)
- Tools: Dependabot, Snyk, OWASP Dependency-Check
- Block deployments with critical vulnerabilities

**Dependency Updates**:
- Patch critical vulnerabilities within 7 days
- Update dependencies monthly (routine)
- Test updates before deploying

**Example Workflow**:
```yaml
# GitHub Actions: Dependency scanning
name: Security Scan
on: [push]
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2
      - name: Run Snyk
        run: snyk test --severity-threshold=high
```

### 5.4 API Security

**Authentication**:
- API keys for service-to-service
- JWT tokens for user requests
- OAuth 2.0 for third-party integrations

**Rate Limiting**:
- Prevent abuse (DDoS, brute force)
- Limits: 100 requests/minute per IP, 1,000 requests/minute per API key
- Return HTTP 429 (Too Many Requests) when exceeded

**Input Validation**:
- Validate all inputs (type, length, format)
- Reject invalid requests (HTTP 400 Bad Request)
- Use schema validation (JSON Schema, Pydantic)

**Example**:
```python
from pydantic import BaseModel, validator

class QueryRequest(BaseModel):
    query: str
    
    @validator('query')
    def validate_query(cls, v):
        if len(v) > 500:
            raise ValueError("Query too long (max 500 characters)")
        if not v.strip():
            raise ValueError("Query cannot be empty")
        return v
```

**HTTPS Only**:
- All APIs HTTPS (no HTTP)
- HSTS header (HTTP Strict Transport Security)
- Certificate pinning (mobile apps)

## 6. Encryption Standards

### 6.1 Encryption Algorithms

**Symmetric Encryption** (same key for encrypt/decrypt):
- **Algorithm**: AES-256 (Advanced Encryption Standard)
- **Mode**: GCM (Galois/Counter Mode) for authenticated encryption
- **Use Cases**: Data at rest, session encryption

**Asymmetric Encryption** (public/private key pair):
- **Algorithm**: RSA 2048-bit or Ed25519
- **Use Cases**: Key exchange, digital signatures, SSH keys

**Hashing** (one-way, for passwords):
- **Algorithm**: bcrypt or Argon2
- **Salt**: Unique salt per password (16 bytes minimum)
- **Cost Factor**: 12+ (adjust to take ~100-500ms)

**Deprecated Algorithms** (do not use):
-  DES, 3DES (too weak)
-  MD5, SHA-1 for security purposes (collision attacks)
-  RSA < 2048-bit (too weak)

### 6.2 Key Management

**Key Generation**:
- Use cryptographically secure random number generator (CSRNG)
- Never generate keys manually or predictably

```python
#  Good: Secure random key generation
import secrets
key = secrets.token_bytes(32)  # 256-bit key
```

**Key Storage**:
- **Application Keys**: AWS Secrets Manager or HashiCorp Vault
- **Database Encryption Keys**: Hardware Security Module (HSM) or AWS KMS
- **SSH Private Keys**: Encrypted with passphrase, stored in ~/.ssh
- **Never**: Hardcode keys in source code, store in unencrypted files

**Key Rotation**:
- **Encryption Keys**: Rotate annually (or if compromised)
- **API Keys**: Rotate semi-annually
- **Certificates**: Rotate before expiration (auto-renewal preferred)

**Key Rotation Process**:
```
1. Generate new key
2. Deploy new key alongside old key (dual-key period)
3. Update applications to use new key
4. After verification, revoke old key
5. Document rotation in key management log
```

### 6.3 Certificate Management

**TLS Certificates**:
- Use trusted Certificate Authority (Let's Encrypt, DigiCert)
- Validity: Maximum 1 year (auto-renewal recommended)
- Algorithm: RSA 2048-bit or ECDSA P-256

**Certificate Monitoring**:
- Monitor expiration (alerts 30 days before)
- Auto-renewal (Let's Encrypt with Certbot)
- Certificate transparency logging (monitor for unauthorized certificates)

**Example Auto-Renewal**:
```bash
# Certbot auto-renewal (cron job)
0 0 * * * certbot renew --quiet && systemctl reload nginx
```

## 7. Vulnerability Management

### 7.1 Vulnerability Scanning

**Automated Scanning**:
- **Frequency**: Weekly (or after major changes)
- **Tools**: Nessus, OpenVAS, Qualys
- **Scope**: All servers, applications, network devices

**Scan Types**:
- **Network Scan**: Identify open ports, services, vulnerabilities
- **Application Scan**: OWASP Top 10, injection flaws, XSS
- **Configuration Scan**: Check for misconfigurations (default passwords, unnecessary services)

**Vulnerability Severity**:
```
CRITICAL (CVSS 9.0-10.0):
- Remote code execution, authentication bypass
- Action: Patch within 24 hours

HIGH (CVSS 7.0-8.9):
- SQL injection, privilege escalation
- Action: Patch within 7 days

MEDIUM (CVSS 4.0-6.9):
- Information disclosure, minor XSS
- Action: Patch within 30 days

LOW (CVSS 0.1-3.9):
- Minor issues, no security impact
- Action: Patch as convenient
```

### 7.2 Patch Management

**Patching Schedule**:
- **Critical Patches**: Within 24 hours (emergency change process)
- **High Patches**: Within 7 days (scheduled maintenance)
- **Medium/Low Patches**: Monthly patching cycle (Patch Tuesday)

**Patch Testing**:
1. Test patch in development environment
2. Verify functionality (automated tests)
3. Deploy to staging
4. If successful, deploy to production
5. Monitor for issues

**Patch Exceptions**:
- If patch breaks critical functionality, delay and document
- Implement compensating controls (WAF rule, disable feature)
- Re-evaluate monthly

### 7.3 Penetration Testing

**Annual Penetration Test**:
- Conducted by external security firm
- Scope: All internet-facing systems
- Duration: 1-2 weeks
- Report: Findings, severity, recommendations

**Penetration Test Types**:
- **Black Box**: No internal knowledge (simulates external attacker)
- **Gray Box**: Limited knowledge (simulates insider with partial access)
- **White Box**: Full knowledge (comprehensive security review)

**Remediation**:
- Critical findings: Fix within 30 days
- High findings: Fix within 60 days
- Medium/Low findings: Fix within 90 days
- Retest after remediation

## 8. Incident Response

### 8.1 Security Incident Types

**Types of Incidents**:
- **Malware Infection**: Virus, ransomware, trojan
- **Phishing Attack**: Employee clicks malicious link, provides credentials
- **Data Breach**: Unauthorized access to sensitive data
- **Insider Threat**: Employee intentionally or accidentally leaks data
- **DDoS Attack**: Service unavailable due to traffic flood
- **Account Compromise**: Attacker gains access to user account

### 8.2 Incident Response Process

**Phase 1: Detection** (0-15 min):
- Alert received (automated monitoring, user report)
- Initial triage (confirm incident vs. false alarm)
- Classify severity (Critical, High, Medium, Low)

**Phase 2: Containment** (15-60 min):
- Isolate affected systems (disconnect from network)
- Disable compromised accounts
- Prevent further damage

**Phase 3: Eradication** (1-4 hours):
- Remove malware
- Patch vulnerabilities
- Reset passwords

**Phase 4: Recovery** (4-24 hours):
- Restore systems from clean backups
- Verify systems clean (no persistence mechanisms)
- Monitor for reinfection

**Phase 5: Lessons Learned** (1 week after):
- Post-incident review (what happened, why, how to prevent)
- Update procedures
- Train employees

### 8.3 Reporting Security Incidents

**How to Report**:
- Email: security@company.com
- Phone: (555) 123-4580 (24/7 hotline)
- Slack: DM @security-team
- In-person: Security team office

**Report Immediately**:
- Suspicious email (phishing)
- Lost/stolen device
- Suspected account compromise
- Malware infection
- Data breach or leak
- Unusual system behavior

**What to Include**:
- Your name and contact info
- What happened (detailed description)
- When it happened (date, time)
- Systems affected
- Actions taken (if any)

**No Penalties**:
- Reporting security issues is encouraged
- No punishment for honest mistakes
- Protection under whistleblower policy

## 9. Business Continuity & Disaster Recovery

### 9.1 Business Continuity Plan (BCP)

**Objective**: Ensure critical business functions continue during disruption

**Critical Business Functions**:
1. RAG Query System (Priority 1)
2. Customer Support (Priority 1)
3. Internal Communication (Priority 2)
4. Payroll (Priority 2)

**Recovery Time Objective (RTO)**: 4 hours (maximum downtime)
**Recovery Point Objective (RPO)**: 1 hour (maximum data loss)

### 9.2 Disaster Scenarios

**Scenario 1: Data Center Outage**:
- Impact: All systems unavailable
- Mitigation: Failover to secondary data center (AWS region)
- Recovery: 2 hours (automated failover)

**Scenario 2: Ransomware Attack**:
- Impact: Files encrypted, systems unusable
- Mitigation: Restore from backups (offline, uninfected)
- Recovery: 6 hours (restore from previous day backup)

**Scenario 3: Natural Disaster** (fire, flood, earthquake):
- Impact: Office inaccessible, equipment destroyed
- Mitigation: Remote work capabilities, cloud infrastructure
- Recovery: Immediate (all systems cloud-based)

### 9.3 Backup Strategy

**Backup Schedule**:
- **Full Backup**: Daily (2 AM)
- **Incremental Backup**: Hourly (during business hours)
- **Retention**: 30 days (daily backups), 1 year (monthly backups)

**Backup Locations**:
- **Primary**: AWS S3 (us-east-1)
- **Secondary**: Azure Blob Storage (eu-west-1)
- **Offline**: Monthly backup to encrypted external drive (stored offsite)

**What's Backed Up**:
-  Databases (Milvus, PostgreSQL)
-  Application code (Git repositories)
-  Configuration files (environment variables, docker-compose.yml)
-  User data (documents, conversation history)
-  Logs (last 90 days)
-  Temporary files, caches (not critical)

**Backup Encryption**:
- All backups encrypted at rest (AES-256)
- Encryption keys stored separately (AWS KMS)

**Backup Testing**:
- Test restore monthly (ensure backups are valid)
- Full disaster recovery drill quarterly
- Document test results

### 9.4 Disaster Recovery Procedures

**Milvus Restore**:
```bash
# 1. Stop Milvus
docker-compose stop milvus-standalone

# 2. Restore data from backup
aws s3 cp s3://backups/milvus-backup-20251012.tar.gz /tmp/
tar -xzf /tmp/milvus-backup-20251012.tar.gz -C ./volumes/milvus/

# 3. Start Milvus
docker-compose up -d milvus-standalone

# 4. Verify data integrity
python backend/verify_milvus_data.py
```

**Full System Restore**:
```bash
# 1. Provision new infrastructure (AWS, Docker hosts)
terraform apply

# 2. Restore application code
git clone https://github.com/company/rag-system.git
git checkout <last-known-good-commit>

# 3. Restore configuration
aws s3 cp s3://backups/config-backup-20251012.tar.gz /tmp/
tar -xzf /tmp/config-backup-20251012.tar.gz

# 4. Restore databases (see above)

# 5. Deploy application
docker-compose up -d

# 6. Verify functionality
pytest backend/tests/e2e/

# 7. Update DNS (cutover to new infrastructure)
# 8. Monitor closely for 24 hours
```

## 10. Compliance & Regulatory Requirements

### 10.1 Applicable Regulations

**General Data Protection Regulation (GDPR)**:
- Applies to: EU residents' personal data
- Key Requirements:
  - Consent for data collection
  - Right to access, rectify, erase data
  - Data breach notification (within 72 hours)
  - Data protection by design

**California Consumer Privacy Act (CCPA)**:
- Applies to: California residents
- Key Requirements:
  - Disclose data collection practices
  - Right to opt-out of data sale
  - Right to delete personal data

**Payment Card Industry Data Security Standard (PCI DSS)**:
- Applies to: If we process credit cards
- Key Requirements:
  - Secure cardholder data
  - Encrypt transmissions
  - Restrict access
  - Regular security testing

**Health Insurance Portability and Accountability Act (HIPAA)**:
- Applies to: If we handle health information
- Key Requirements:
  - Protect patient privacy
  - Secure health records
  - Breach notification
  - Business associate agreements

**SOC 2 (Service Organization Control 2)**:
- Voluntary framework for service providers
- Five Trust Service Criteria: Security, Availability, Processing Integrity, Confidentiality, Privacy

### 10.2 GDPR Compliance

**Data Subject Rights**:

**Right to Access**:
- User requests copy of their data
- Response: Within 30 days, provide data in machine-readable format (JSON, CSV)

**Right to Rectification**:
- User requests correction of inaccurate data
- Response: Update data within 30 days

**Right to Erasure** ("Right to be Forgotten"):
- User requests deletion of their data
- Response: Delete within 30 days (unless legal obligation to retain)

**Right to Data Portability**:
- User requests data in portable format
- Response: Provide data in JSON or CSV within 30 days

**Procedure for Data Subject Requests**:
1. User submits request via privacy@company.com
2. Verify identity (prevent fraudulent requests)
3. Locate all user data (databases, backups, logs)
4. Fulfill request within 30 days
5. Document request and fulfillment

**Data Breach Notification**:
- **Timeline**: Notify supervisory authority within 72 hours
- **Content**: What happened, data affected, mitigation steps, contact info
- **Affected Users**: Notify if high risk to rights and freedoms

### 10.3 SOC 2 Compliance

**SOC 2 Controls**:

**Security**:
- Access controls (MFA, RBAC)
- Encryption (at rest and in transit)
- Vulnerability management
- Incident response

**Availability**:
- Uptime monitoring (99.9% SLA)
- Disaster recovery plan
- Regular backups

**Processing Integrity**:
- Data validation (input/output)
- Error handling and logging
- Change management

**Confidentiality**:
- Data classification
- Secure data disposal
- Non-disclosure agreements (NDAs)

**Privacy**:
- Privacy policy
- Consent management
- Data retention policies

**SOC 2 Audit**:
- Conducted annually by external auditor
- Type 1: Controls exist at point in time
- Type 2: Controls operate effectively over period (6-12 months)

## 11. Third-Party Security

### 11.1 Vendor Risk Management

**Vendor Security Assessment**:
- Conduct before engaging vendor
- Review: Security policies, certifications (SOC 2, ISO 27001), breach history
- Request: Security questionnaire, penetration test results

**Vendor Tiers**:

**Tier 1 (Critical)**:
- Access to customer data or critical systems
- Examples: Cloud provider (AWS), database hosting
- Assessment: Full security review, annual audits

**Tier 2 (High)**:
- Access to internal data
- Examples: HR system, accounting software
- Assessment: Security questionnaire, certifications

**Tier 3 (Medium/Low)**:
- Minimal access
- Examples: Marketing tools, analytics
- Assessment: Basic security review

### 11.2 Vendor Contracts

**Security Clauses Required**:
- **Data Protection**: Vendor must protect our data per our standards
- **Incident Notification**: Notify within 24 hours of breach
- **Audit Rights**: We can audit vendor's security controls
- **Data Deletion**: Delete our data upon contract termination
- **Compliance**: Vendor must comply with applicable regulations (GDPR, CCPA)
- **Liability**: Vendor liable for breaches caused by their negligence

**Data Processing Agreement (DPA)**:
- Required for vendors processing personal data (GDPR requirement)
- Specifies: Purpose, data types, retention, security measures

### 11.3 API Integrations

**Third-Party APIs**:
- Review API security (HTTPS, authentication, rate limiting)
- Store API keys securely (secret manager, not hardcoded)
- Monitor API usage (detect compromise)
- Rotate API keys regularly (semi-annually)

**API Key Management**:
```python
#  Bad: Hardcoded API key
api_key = "sk-1234567890"

#  Good: Environment variable
import os
api_key = os.getenv("THIRD_PARTY_API_KEY")

#  Better: Secret manager
from aws_secretsmanager import get_secret
api_key = get_secret("third-party-api-key")
```

## 12. Employee Security Responsibilities

### 12.1 Security Awareness Training

**Mandatory Training**:
- **New Hires**: Security awareness training (first week)
- **Annual Training**: All employees (refresher)
- **Phishing Training**: Simulated phishing emails quarterly
- **Role-Specific**: Developers (secure coding), admins (privileged access)

**Training Topics**:
- Password security
- Phishing recognition
- Data classification and handling
- Incident reporting
- Physical security
- Remote work security

**Training Compliance**: 100% completion required, HR tracks compliance

### 12.2 Acceptable Use Policy

**Permitted Use**:
- Work-related activities
- Reasonable personal use (checking email, news during breaks)
- Professional development (online courses)

**Prohibited Use**:
- Illegal activities (piracy, hacking)
- Accessing inappropriate content (pornography, hate speech)
- Installing unauthorized software
- Circumventing security controls
- Excessive personal use (gaming, streaming during work hours)

**Monitoring**:
- Company reserves right to monitor device usage
- No expectation of privacy on company devices
- Monitoring for security purposes (detect malware, data exfiltration)

### 12.3 Clean Desk Policy

**Requirements**:
- Lock confidential documents when not in use
- Clear desk at end of day (no sensitive documents left out)
- Shred documents when no longer needed
- Lock computer screen when away (Windows+L or Ctrl+Cmd+Q)

**Desk Audit**: Random spot checks quarterly

### 12.4 Social Engineering Awareness

**Common Tactics**:
- **Phishing**: Fake emails asking for credentials
- **Spear Phishing**: Targeted phishing (appears from colleague, CEO)
- **Vishing**: Phone calls (fake IT support asking for password)
- **Pretexting**: Impersonation (fake vendor, auditor)
- **Baiting**: Leaving infected USB drive (curiosity leads to insertion)

**How to Protect**:
- Verify sender (check email address, not just display name)
- Don't click links in unexpected emails (hover to see actual URL)
- Verify requests via secondary channel (call person if CEO emails urgent wire transfer)
- Report suspicious emails (forward to phishing@company.com)

## 13. Physical Security

### 13.1 Office Access Control

**Badge Access**:
- RFID badge required for entry
- Badges personalized (photo, name, department)
- Lost badge: Report immediately, badge deactivated
- Don't share badge or let others "tailgate" (enter behind you)

**Visitor Management**:
- Visitors register at front desk (photo ID required)
- Visitor badge issued (expires same day)
- Escorted by employee at all times
- Visitor log maintained

**Restricted Areas**:
- Server room: Badge + PIN + manager approval
- Executive offices: Badge + authorized list
- Confidential meeting rooms: Badge + room reservation

### 13.2 Device Security

**Laptop Security**:
- Use laptop lock (Kensington lock) in public spaces
- Don't leave laptop unattended in car (visible target)
- Encrypt laptop (FileVault on Mac, BitLocker on Windows)

**Mobile Device Security**:
- Enable passcode/biometrics (Face ID, Touch ID, fingerprint)
- Enable remote wipe (Find My iPhone, Find My Device)
- Report lost/stolen devices immediately (IT remotely wipes)

**USB Devices**:
- Don't use unknown USB drives (malware risk)
- Encrypt USB drives with sensitive data
- Disable autorun (Windows)

### 13.3 Secure Disposal

**Device Disposal**:
- IT handles all device disposal (don't throw away yourself)
- Hard drives: Securely wiped (7x overwrite) or physically destroyed
- Certificate of destruction provided

**Document Disposal**:
- Use cross-cut shredder (particles <4mm)
- Shred bins available (secure destruction vendor empties weekly)

## 14. Security Monitoring & Auditing

### 14.1 Security Monitoring

**24/7 Monitoring**:
- Security Information and Event Management (SIEM): Splunk or ELK
- Monitors: Logins, access attempts, network traffic, system changes

**Alerts**:
- Failed login attempts (5 within 5 minutes)
- Privileged access (admin commands)
- Data exfiltration (large data transfers)
- Malware detection
- Configuration changes (firewall rules, user permissions)

**Security Operations Center (SOC)**:
- Team monitors alerts 24/7
- Investigates suspicious activity
- Escalates incidents as needed

### 14.2 Audit Logging

**What's Logged**:
- User logins (successful and failed)
- Access to sensitive data (customer records, financial data)
- Privileged commands (sudo, admin actions)
- Configuration changes
- Network connections

**Log Retention**:
- Security logs: 1 year
- Access logs: 90 days
- Application logs: 30 days

**Log Protection**:
- Logs encrypted at rest
- Logs sent to centralized system (tamper-proof)
- Alerts on log deletion or tampering

### 14.3 Access Reviews

**Quarterly Access Review**:
- Managers review team's access
- Remove unnecessary access
- Report to security team

**Annual Access Audit**:
- Security team audits all access (comprehensive review)
- Identify over-privileged accounts
- Enforce least privilege

### 14.4 Security Metrics

**Key Metrics**:
- **Mean Time to Detect (MTTD)**: Time from incident start to detection (target: <15 min)
- **Mean Time to Respond (MTTR)**: Time from detection to containment (target: <1 hour)
- **Vulnerabilities**: Count by severity (target: 0 critical, <5 high)
- **Patch Compliance**: % systems patched on time (target: 95%+)
- **Training Compliance**: % employees completed training (target: 100%)
- **Phishing Click Rate**: % employees click simulated phishing (target: <5%)

**Security Dashboard**:
- Real-time metrics on Grafana dashboard
- Executive report monthly (trends, major incidents)
