## 1. Why Docker & Docker Compose?

### Business Justification

**Problem Statement**:
- Different environments (dev, staging, prod) had inconsistent setups
- "Works on my machine" syndrome
- Dependency conflicts between system packages
- Hours wasted on environment setup for new developers
- Difficult to scale and replicate infrastructure

**Docker Solution**:
- **Consistency**: Same environment everywhere (dev laptop = prod server)
- **Isolation**: Each service in its own container, no conflicts
- **Portability**: Run anywhere Docker runs (AWS, Azure, GCP, on-prem)
- **Reproducibility**: Infrastructure as code (docker-compose.yml)
- **Speed**: New developer productive in <10 minutes

### Technical Benefits

```yaml
# Before Docker (Manual Setup):
# 1. Install Python 3.10
# 2. Install system dependencies (libopenblas, etc.)
# 3. Create virtual environment
# 4. Install pip packages
# 5. Install Node.js 18
# 6. Install npm packages
# 7. Install Milvus (complex!)
# 8. Install Ollama
# 9. Configure networking
# 10. Start all services manually
# Time: 2-4 hours
# Success rate: 60% (dependency conflicts)

# With Docker:
$ docker compose up --build
# Time: 5 minutes (first time), 30 seconds (subsequent)
# Success rate: 99% (deterministic)
```

### Docker vs Alternatives

| Approach | Pros | Cons | Verdict |
|----------|------|------|---------|
| **Docker** | Consistent, portable, isolated | Learning curve, overhead |  **SELECTED** |
| VMs | Strong isolation | Heavy (GB), slow startup |  Too resource-heavy |
| Conda/venv | Native Python | Python-only, no Milvus |  Incomplete solution |
| Kubernetes | Production-scale orchestration | Overkill for POC |  Future consideration |
| Bare Metal | Maximum performance | No isolation, fragile |  Not reproducible |

### Why Docker Compose (not just Docker)?

```bash
# Without Compose - Managing 6 services manually:
docker run -d --name etcd ...
docker run -d --name minio ...
docker run -d --name milvus --link etcd --link minio ...
docker run -d --name ollama ...
docker run -d --name backend --link milvus --link ollama ...
docker run -d --name frontend --link backend ...

# With Compose - One command:
docker compose up -d

# Compose advantages:
#  Dependency management (depends_on)
#  Network creation (automatic service discovery)
#  Volume management (persistent data)
#  Environment variables (centralized .env)
#  Multi-service orchestration
#  Easy scaling (docker compose scale backend=3)
```

### Base Image Choices

```dockerfile
# Frontend: nginx:alpine
# Why Alpine?
# - Smallest base image: 5 MB vs 130 MB (debian)
# - Sufficient for static file serving
# - Security: Minimal attack surface
# - Nginx: Battle-tested, high performance

# Backend: python:3.10-slim
# Why Slim (not Alpine)?
# - Alpine uses musl libc (compatibility issues with ML libraries)
# - Slim uses glibc (standard, better compatibility)
# - Still small: 122 MB vs 1 GB (full python image)
# - All Python packages work correctly

# Milvus, etcd, MinIO, Ollama: Official images
# - Maintained by vendors
# - Security updates
# - Optimized for production
```

## 3. Docker Compose Configuration Explained

### Complete docker-compose.yml Breakdown

```yaml
version: '3.8'

# Why version 3.8?
# - Supports all features we need (depends_on, healthchecks, etc.)
# - Compatible with Docker Compose 1.25.0+ (widely available)
# - Version 3.9+ doesn't add features we need

services:
  # ============================================
  # FRONTEND SERVICE
  # ============================================
  frontend:
    build:
      context: ./frontend
      dockerfile: Dockerfile
    container_name: rag-frontend
    ports:
      - "3000:80"
    # Why port mapping 3000:80?
    # - Host port 3000 (user accesses)
    # - Container port 80 (nginx default)
    # - Could use 80:80 but 3000 avoids conflicts
    environment:
      - REACT_APP_API_URL=http://localhost:8000
    # Why environment variable?
    # - Frontend needs to know backend URL
    # - Injected at build time into React app
    # - localhost:8000 works because user's browser makes request
    depends_on:
      - backend
    # Why depends_on?
    # - Ensures backend starts before frontend
    # - Prevents frontend starting with no API
    networks:
      - rag-network
    restart: unless-stopped
    # Why unless-stopped?
    # - Auto-restart on failure
    # - Don't restart if manually stopped
    # - Good for production reliability

  # ============================================
  # BACKEND SERVICE
  # ============================================
  backend:
    build:
      context: ./backend
      dockerfile: Dockerfile
      # Multi-stage build for optimization
    container_name: rag-backend
    ports:
      - "8000:8000"
    environment:
      - MILVUS_HOST=milvus-standalone
      # Why "milvus-standalone" not "localhost"?
      # - Docker Compose creates internal DNS
      # - Service names resolve to container IPs
      # - localhost would be backend container itself
      - MILVUS_PORT=19530
      - MISTRAL_API_URL=http://ollama:11434/api/generate
      # Same DNS resolution for Ollama
      - LLM_MODE=api
    volumes:
      - ./data:/app/data
      # Why volume mount?
      # - Share data directory with host
      # - Allows adding documents without rebuilding
      # - Data persists across container restarts
      - ./backend/results:/app/results
      # Evaluation results accessible on host
    depends_on:
      - milvus-standalone
      - ollama
    networks:
      - rag-network
    restart: unless-stopped
    mem_limit: 6g
    # Why memory limit?
    # - Embedding model uses ~4 GB
    # - Prevents OOM killing other containers
    # - Ensures predictable resource usage
    cpus: 4
    # Why CPU limit?
    # - Prevents hogging all CPU during inference
    # - Ensures responsive system
    # - 4 cores sufficient for embedding + API

  # ============================================
  # MILVUS VECTOR DATABASE
  # ============================================
  milvus-standalone:
    image: milvusdb/milvus:v2.3.0
    container_name: rag-milvus
    command: ["milvus", "run", "standalone"]
    environment:
      ETCD_ENDPOINTS: etcd:2379
      MINIO_ADDRESS: minio:9000
      MINIO_ACCESS_KEY: minioadmin
      MINIO_SECRET_KEY: minioadmin
    volumes:
      - milvus-data:/var/lib/milvus
      # Why named volume (not bind mount)?
      # - Docker manages storage location
      # - Better performance on Mac/Windows
      # - Automatic cleanup with "docker volume rm"
    ports:
      - "19530:19530"
      # Why expose 19530?
      # - Allows external tools (Attu UI, debugging)
      # - Not required for internal communication
      # - Can remove in production for security
    depends_on:
      - etcd
      - minio
    networks:
      - rag-network
    restart: unless-stopped
    mem_limit: 4g
    cpus: 2

  # ============================================
  # ETCD (Milvus Metadata Store)
  # ============================================
  etcd:
    image: quay.io/coreos/etcd:v3.5.5
    container_name: rag-etcd
    environment:
      - ETCD_AUTO_COMPACTION_MODE=revision
      - ETCD_AUTO_COMPACTION_RETENTION=1000
      - ETCD_QUOTA_BACKEND_BYTES=4294967296
      # Why these settings?
      # - Auto-compaction prevents unbounded growth
      # - Retention=1000 keeps recent history
      # - Quota=4GB max database size
      - ETCD_SNAPSHOT_COUNT=50000
    volumes:
      - etcd-data:/etcd
    command: >
      etcd
      --advertise-client-urls=http://etcd:2379
      --listen-client-urls=http://0.0.0.0:2379
      --data-dir=/etcd
    networks:
      - rag-network
    restart: unless-stopped
    mem_limit: 1g

  # ============================================
  # MINIO (Milvus Object Storage)
  # ============================================
  minio:
    image: minio/minio:RELEASE.2023-03-20T20-16-18Z
    container_name: rag-minio
    environment:
      MINIO_ROOT_USER: minioadmin
      MINIO_ROOT_PASSWORD: minioadmin
      # Why hardcoded credentials?
      # - Only accessible within Docker network
      # - Not exposed to internet
      # - Change in production if exposing ports
    volumes:
      - minio-data:/minio_data
    command: >
      minio server /minio_data
      --console-address ":9001"
    ports:
      - "9000:9000"
      - "9001:9001"
      # Why expose ports?
      # - 9000: API endpoint (optional)
      # - 9001: Web UI for debugging (optional)
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:9000/minio/health/live"]
      interval: 30s
      timeout: 20s
      retries: 3
      # Why healthcheck?
      # - Ensures MinIO is ready before Milvus starts
      # - Prevents Milvus connection errors
    networks:
      - rag-network
    restart: unless-stopped
    mem_limit: 1g

  # ============================================
  # OLLAMA (LLM Inference Server)
  # ============================================
  ollama:
    image: ollama/ollama:latest
    container_name: rag-ollama
    volumes:
      - ollama-data:/root/.ollama
      # Why volume for Ollama?
      # - Stores model files (~4.4 GB for Mistral)
      # - Persists across container restarts
      # - Avoids re-downloading model
    ports:
      - "11434:11434"
    environment:
      - OLLAMA_HOST=0.0.0.0
      # Why 0.0.0.0?
      # - Listen on all interfaces (accessible from other containers)
      # - Default is localhost (only accessible within container)
    networks:
      - rag-network
    restart: unless-stopped
    mem_limit: 10g
    # Why 10 GB?
    # - Mistral 7B Q4 uses ~6 GB
    # - Need headroom for inference
    cpus: 4
    # Can increase to 8 for faster inference

# ============================================
# NETWORKS
# ============================================
networks:
  rag-network:
    driver: bridge
    # Why bridge network?
    # - Allows service-to-service communication
    # - Built-in DNS resolution (service names)
    # - Isolated from other Docker networks
    # - Default but explicit declaration preferred

# ============================================
# VOLUMES
# ============================================
volumes:
  milvus-data:
    # Vector database data (embeddings, indexes)
  etcd-data:
    # Metadata storage
  minio-data:
    # Object storage
  ollama-data:
    # LLM models
  # Why named volumes?
  #  Docker manages storage location
  #  Persist across container recreation
  #  Can backup/restore with docker commands
  #  Better performance than bind mounts
```

## 4. Networking Architecture

### Docker Network Types

```bash
# Bridge Network (Our Choice): 
# - Default for Docker Compose
# - Services communicate via service names
# - Isolated from host network
# - DNS resolution built-in

# Example: Backend connects to Milvus
# Inside backend container:
curl http://milvus-standalone:19530
# DNS resolves "milvus-standalone" to container IP (e.g., 172.18.0.3)

# Host Network:
# - Container uses host's network stack
# - No isolation
# - No port mapping needed
# - Not recommended for multi-container apps

# None Network:
# - No networking
# - Completely isolated
# - Use for security-critical tasks
```

### Service Discovery & DNS

```yaml
# How services find each other:

services:
  backend:
    environment:
      - MILVUS_HOST=milvus-standalone  # ← Service name
      - MILVUS_PORT=19530

# Docker Compose creates DNS entries:
# milvus-standalone → 172.18.0.3
# backend → 172.18.0.4
# ollama → 172.18.0.5

# Benefits:
#  No hardcoded IPs
#  Works across different environments
#  Survives container recreation
```

### Port Mapping Strategy

```yaml
# Internal vs External Ports

frontend:
  ports:
    - "3000:80"
    # Host:Container
    # User accesses localhost:3000
    # Nginx listens on container port 80

backend:
  ports:
    - "8000:8000"
    # Same port for simplicity
    # Could be "8080:8000" if 8000 is taken

milvus:
  ports:
    - "19530:19530"
    # Optional - only for external tools
    # Remove in production for security
```

### Network Isolation & Security

```yaml
# Production setup: Multiple networks

networks:
  frontend-network:  # Frontend ↔ Backend only
  backend-network:   # Backend ↔ Databases only
  database-network:  # Databases internal only

services:
  frontend:
    networks:
      - frontend-network
  backend:
    networks:
      - frontend-network
      - backend-network
  milvus:
    networks:
      - backend-network
      - database-network
  # Result:
  #  Frontend cannot directly access databases
  #  Least privilege networking
  #  Reduced attack surface
```

## 5. Volume Management & Data Persistence

### Volume Types Explained

```yaml
# Named Volumes (Recommended): 
volumes:
  milvus-data:
  # Docker manages where data is stored
  # Location: /var/lib/docker/volumes/milvus-data/_data
  # Benefits:
  #  Portable across hosts
  #  Better performance
  #  Easy backup/restore

# Bind Mounts:
volumes:
  - ./data:/app/data
  # Host directory → Container directory
  # Benefits:
  #  Easy to edit files on host
  #  Good for development
  #  Path dependencies (less portable)

# Tmpfs Mounts:
tmpfs:
  - /tmp
  # RAM-based temporary filesystem
  # Benefits:
  #  Very fast
  #  Auto-cleaned on restart
  #  Not persistent
```

### Data Persistence Map

```
Host Machine
├── ./data (bind mount)
│   ├── hr_policy.txt → /app/data/hr_policy.txt (backend)
│   ├── onboarding.txt → /app/data/onboarding.txt (backend)
│   └── sample_confluence_pages/
│
├── ./backend/results (bind mount)
│   └── results.md → /app/results/results.md (backend)
│
└── Docker Volumes (named volumes)
    ├── milvus-data (vector embeddings & indexes)
    │   └── /var/lib/docker/volumes/milvus-data/
    │       └── _data/ (binary data)
    ├── etcd-data (Milvus metadata)
    ├── minio-data (Milvus object storage)
    └── ollama-data (Mistral model files ~4.4 GB)
```

### Volume Operations

```bash
# List volumes
docker volume ls

# Inspect volume (see mount point)
docker volume inspect rag-enterprise_milvus-data

# Backup volume
docker run --rm \
  -v rag-enterprise_milvus-data:/data \
  -v $(pwd):/backup \
  alpine tar czf /backup/milvus-backup.tar.gz /data

# Restore volume
docker run --rm \
  -v rag-enterprise_milvus-data:/data \
  -v $(pwd):/backup \
  alpine tar xzf /backup/milvus-backup.tar.gz -C /

# Remove unused volumes
docker volume prune

# Remove specific volume (WARNING: Data loss!)
docker volume rm rag-enterprise_milvus-data
```

### Variable Loading Priority

```
1. Environment variables (highest priority)
   export MILVUS_HOST=custom-milvus
   docker compose up

2. .env file in compose directory
   MILVUS_HOST=milvus-standalone

3. Default values in docker-compose.yml
   environment:
     - MILVUS_HOST=${MILVUS_HOST:-milvus-standalone}
     # ${VAR:-default} means use VAR or default if unset

4. Application defaults (lowest priority)
   MILVUS_HOST = os.getenv("MILVUS_HOST", "localhost")
```

## 7. Build Process & Optimization

### Multi-Stage Builds

```dockerfile
# Backend Dockerfile (Optimized)

# ============================================
# Stage 1: Builder (Dependencies)
# ============================================
FROM --platform=linux/arm64/v8 python:3.10-slim AS builder

WORKDIR /app

# Install build dependencies
RUN apt-get update && apt-get install -y --no-install-recommends \
    build-essential \
    gcc \
    g++ \
    && rm -rf /var/lib/apt/lists/*

# Install Python dependencies
COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

# Why --user?
# - Installs to ~/.local (easier to copy to final stage)
# - Doesn't require root in final stage

# Why --no-cache-dir?
# - Saves 200-300 MB
# - pip cache not needed in container

# ============================================
# Stage 2: Runtime (Slim)
# ============================================
FROM --platform=linux/arm64/v8 python:3.10-slim

WORKDIR /app

# Install only runtime dependencies (no build tools)
RUN apt-get update && apt-get install -y --no-install-recommends \
    libopenblas-dev \
    libomp-dev \
    && rm -rf /var/lib/apt/lists/*

# Copy installed packages from builder
COPY --from=builder /root/.local /root/.local

# Copy application code
COPY . .

# Make sure scripts are executable
RUN chmod +x /app/*.py

ENV PATH=/root/.local/bin:$PATH

CMD ["python", "main.py"]

# Benefits of Multi-Stage:
# - Final image: 2.1 GB (without: 3.5 GB)
# - Savings: 1.4 GB (40% reduction)
# - No build tools in production image
# - Faster deployment (less to transfer)
```

### Build Optimization Techniques

```dockerfile
#  Bad: Rebuilds everything on code change
COPY . .
RUN pip install -r requirements.txt

#  Good: Layer caching
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
# Now code changes don't trigger pip install

#  Bad: Large layers
RUN apt-get update
RUN apt-get install -y package1
RUN apt-get install -y package2
RUN rm -rf /var/lib/apt/lists/*

#  Good: Minimize layers, clean in same layer
RUN apt-get update && \
    apt-get install -y package1 package2 && \
    rm -rf /var/lib/apt/lists/*

#  Bad: Including unnecessary files
COPY . .

#  Good: Use .dockerignore
# .dockerignore:
__pycache__
*.pyc
.git
.env
tests/
*.md
```

### Build Time Comparison

```bash
# Without optimization:
docker build -t backend:old .
# Time: 8 minutes
# Size: 3.5 GB

# With optimization (multi-stage + caching):
docker build -t backend:new .
# Time: 3 minutes (first build)
# Time: 30 seconds (code change rebuild)
# Size: 2.1 GB

# Savings:
# Time: 62% faster
# Size: 40% smaller
```

## 8. Startup Sequence & Health Checks

### Startup Order

```yaml
# Dependency Graph & Timing

1. etcd & MinIO (0-10 seconds)
   └─ Start in parallel
   └─ Wait for readiness probes

2. Milvus (10-20 seconds)
   └─ depends_on: etcd, MinIO
   └─ Wait for services to be healthy
   └─ Initialize database

3. Ollama (0-30 seconds)
   └─ Independent service
   └─ Pull Mistral model if not cached
   └─ Load model into memory

4. Backend (20-120 seconds)
   └─ depends_on: Milvus, Ollama
   └─ Load embedding model (~60 seconds)
   └─ Ingest documents (~30 seconds)
   └─ Start FastAPI server

5. Frontend (0-5 seconds)
   └─ depends_on: Backend
   └─ Serve static files
   └─ Ready immediately

Total Cold Start: ~2-3 minutes
Total Warm Start: ~30 seconds (models cached)
```

### Health Check Implementation

```yaml
# Comprehensive health checks

services:
  backend:
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
      # Checks if FastAPI is responding
      interval: 30s
      # Check every 30 seconds
      timeout: 10s
```

## 9. Resource Limits & Performance Tuning

### Memory Management

```yaml
services:
  backend:
    mem_limit: 6g
    mem_reservation: 4g
    # mem_limit: Hard limit (OOM killer if exceeded)
    # mem_reservation: Soft limit (guaranteed minimum)
    
  milvus:
    mem_limit: 4g
    mem_reservation: 2g
    
  ollama:
    mem_limit: 10g
    mem_reservation: 8g

# Why these limits?
#  Prevents one service from hogging all RAM
#  Ensures stable system performance
#  Triggers alerts before catastrophic failure
#  Allows graceful degradation
```

### CPU Management

```yaml
services:
  backend:
    cpus: 4

    # cpus: Absolute limit (4 cores max)

  frontend:
    cpus: 0.5
    cpu_shares: 256  # Low priority (static files)

#  Ensures responsive API during LLM inference
#  Prioritizes user-facing services
```

## 10. Security Best Practices

### Container Security Checklist

```yaml
#  Security Hardened Configuration

services:
  backend:
    # 1. Use specific image tags (not 'latest')
    image: python:3.10.12-slim  # Not python:latest
    
    # 2. Run as non-root user
    user: "1000:1000"
    # Create user in Dockerfile:
    # RUN useradd -m -u 1000 appuser
    # USER appuser
    
    # 3. Read-only root filesystem
    read_only: true
    tmpfs:
      - /tmp
    # Allow writes only to specific directories
    volumes:
      - ./results:/app/results:rw
      - ./data:/app/data:ro  # Read-only
    
    # 4. Drop unnecessary capabilities
    cap_drop:
      - ALL
    cap_add:
      - NET_BIND_SERVICE  # Only if binding to port < 1024
    
    # 5. No privileged mode
    privileged: false
    
    # 6. Limit network access
    networks:
      backend-network:
        aliases:
          - api-backend
    dns:
      - 8.8.8.8  # Explicit DNS (not host's)
    
    # 7. Security options
    security_opt:
      - no-new-privileges:true  # Prevent privilege escalation
      - apparmor:docker-default  # AppArmor profile
```

### Secrets Management

## 11. Troubleshooting Common Issues

### Issue 1: Backend OOM (Out of Memory)

```bash
# Symptom:
docker compose logs backend
# Error: Killed (OOM)

# Diagnosis:
docker stats backend
# Memory: 6 GB / 6 GB (100% - hitting limit)

# Cause:
# - Embedding model too large for memory
# - Too many concurrent requests
# - Memory leak in application

# Solution 1: Increase memory limit
mem_limit: 8g  # Was 6g

# Solution 2: Use smaller embedding model
# Change from BGE-Large (1024 dim) to BGE-Base (768 dim)

# Solution 3: Add swap space
deploy:
  resources:
    limits:
      memory: 6g
    reservations:
      memory: 4g
```

### Issue 2: Milvus Connection Refused

```bash
# Symptom:
docker compose logs backend
# Error: Connection refused to milvus-standalone:19530

# Diagnosis:
docker compose ps milvus-standalone
# Status: Exited (1)

# Cause:
# - Milvus failed to start
# - etcd or MinIO not ready
# - Port conflict

# Solution 1: Check dependencies
docker compose up etcd minio
docker compose logs etcd minio

# Solution 2: Reset Milvus data
docker compose down -v  # Remove volumes
docker compose up -d

# Solution 3: Check port availability
lsof -i :19530  # See if port is in use
```

### Issue 3: Ollama Model Not Found

```bash
# Symptom:
curl http://localhost:11434/api/generate \
  -d '{"model": "mistral", "prompt": "test"}'
# Error: model "mistral" not found

# Diagnosis:
docker compose exec ollama ollama list
# (empty or missing mistral)

# Cause:
# - Model not pulled
# - Volume not persisted

# Solution:
docker compose exec ollama ollama pull mistral

# Verify:
docker compose exec ollama ollama list
# mistral    f5074b1221da    4.4 GB
```

### Issue 4: Frontend Cannot Reach Backend

```bash
# Symptom:
# Frontend shows "Network Error"
# Browser console: "Failed to fetch http://localhost:8000/ask"

# Diagnosis:
curl http://localhost:8000/health
# Connection refused

# Cause:
# - Backend not started
# - CORS misconfigured
# - Wrong API URL in frontend

# Solution 1: Check backend is running
docker compose ps backend
docker compose logs backend

# Solution 2: Verify CORS
# In backend/main.py:
app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000"],  # Add frontend URL
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)

# Solution 3: Check frontend environment
# In frontend Dockerfile:
ENV REACT_APP_API_URL=http://localhost:8000  # Verify this matches
```

### Issue 5: Slow Query Performance

```bash
# Symptom:
# Queries take > 5 seconds

# Diagnosis:
# Check metrics in response:
# {
#   "embedding_ms": 52,
#   "retrieval_ms": 31,
#   "generation_ms": 4500  ← Slow!
# }

# Cause:
# - LLM inference slow (CPU-bound)
# - No quantization

# Solution 1: Use quantized model
docker compose exec ollama ollama pull mistral:7b-instruct-q4_0

# Solution 2: Add GPU support
# Install nvidia-docker:
services:
  ollama:
    runtime: nvidia
    environment:
      - NVIDIA_VISIBLE_DEVICES=0

# Solution 3: Reduce max tokens
# In llm_client.py:
max_tokens: 300  # Was 500
```

### Issue 6: Docker Compose Version Incompatibility

```bash
# Symptom:
docker compose up
# Error: unsupported Compose file version: 3.8

# Cause:
# - Old Docker Compose version

# Check version:
docker compose version
# Docker Compose version v1.29.2

# Solution:
# Upgrade Docker Compose:
# Mac: Update Docker Desktop
# Linux:
sudo curl -L "https://github.com/docker/compose/releases/download/v2.20.0/docker-compose-$(uname -s)-$(uname -m)" \
  -o /usr/local/bin/docker-compose
sudo chmod +x /usr/local/bin/docker-compose
```
